## Context

См. `proposal.md` — Why. Сейчас root layout вызывает `headers()` и читает установленный `proxy` заголовок `x-resume-locale`, хотя локаль уже присутствует в `[locale]` route params. В Next.js 16 `headers()` является request-time API и препятствует статическому рендерингу дерева. Значения `ru`/`en` независимо повторяются в content registry, `Header`, regex пути, `proxy` matcher и visual scenario.

Одновременно `src/app/globals.css` является точкой подключения глобальных стилей, хранилищем дизайн-токенов и владельцем всех классов компонентов. JSX использует строковые имена классов, включая классы состояния, а responsive-правила сгруппированы по breakpoint в конце общего файла. `HeroField` создаёт случайную геометрию через `Math.random()`, а `FinePointerCursor` поддерживает постоянный animation loop на fine pointer. Текущие Playwright-снимки фиксируют RU/EN-страницы на desktop, tablet и mobile и служат неизменяемым визуальным контрактом миграции.

Рефакторинг должен быть совместим с Next.js 16.3.5: глобальный CSS подключается из root layout, а CSS Modules импортируются непосредственно компонентами. Проект не использует CSS-препроцессор, CSS-in-JS или стороннюю библиотеку компонентов.

## Goals / Non-Goals

**Goals:**

- Сделать владельца каждого компонентного правила очевидным по расположению файла и импорту.
- Ограничить глобальный каскад фундаментальными правилами и небольшим документированным набором общих layout-примитивов.
- Сохранить текущую специфичность, порядок каскада, breakpoint-поведение и внешний вид без обновления эталонных PNG.
- Обеспечить возможность менять компонент и все его responsive/state-стили как одну единицу.
- Оставить стили на стандартном CSS без новых runtime- или build-зависимостей.
- Восстановить возможность статического рендеринга локализованных страниц без request-time API в root layout.
- Устранить ручное дублирование списка поддерживаемых локалей.
- Сделать декоративные клиентские эффекты воспроизводимыми и не выполнять постоянную работу без необходимости.
- Удержать клиентские границы на минимальном уровне интерактивных компонентов.

**Non-Goals:**

- Визуальный редизайн, изменение контента, DOM-семантики, публичных URL или набора локалей.
- Реализация задач из `refine-portfolio-storytelling`.
- Изменение тестов, Playwright-конфигурации, порогов сравнения или эталонных снимков.
- Переход на Tailwind, Sass, CSS-in-JS, utility-first framework или полноценный design-system package.
- Изменение смысла пользовательских взаимодействий либо добавление новой интерактивности.

## Decisions

### 1. Locale-aware layout использует route params

Корневая HTML-разметка переносится под `app/[locale]/layout.tsx`, где `lang` определяется из `params.locale` после проверки поддерживаемой локали. `generateStaticParams` располагается на уровне локализованного сегмента и использует общий registry. Вызов `headers()` и внутренний `x-resume-locale` удаляются.

Корневой `/` продолжает перенаправлять на `/ru`. `proxy` сохраняется только если после удаления заголовка у него остаётся отдельная ответственность, которую нельзя выразить корневым route redirect; иначе файл удаляется. Альтернатива — сохранить header bridge — отклонена, потому что он дублирует route params и переводит статическое дерево в request-time rendering.

### 2. Locale registry является единым источником истины

`src/content` экспортирует readonly registry поддерживаемых локалей и производные `Locale`, `locales` и `isLocale`. `Header` получает варианты переключателя из серверного родителя как сериализуемые данные либо импортирует безопасную общую константу без собственного массива и regex перечня языков. Замена сегмента пути выполняется на основании текущего проверенного locale segment.

Static params, content lookup и навигация используют один registry. `proxy` matcher, если proxy остаётся, не дублирует перечень локалей в нескольких выражениях. Полноценная i18n-библиотека отклонена: две статические локали не требуют новой зависимости.

### 3. Server/client boundaries следуют поведению

Layouts, page composition, metadata и все контентные секции остаются Server Components. Клиентскими остаются только владельцы state, event handlers и browser APIs: меню/переключатель пути, canvas и fine-pointer enhancement. Общие константы, типы и чистые функции размещаются вне client boundary, чтобы их импорт не втягивал серверные модули или контентные словари в browser bundle.

Разделение `Header` на серверную оболочку и небольшой клиентский контрол допустимо, только если оно действительно уменьшает клиентский module graph без изменения DOM. Массовое дробление компонентов ради формального количества `use client` отклонено.

### 4. Трёхуровневая структура CSS

Стили разделяются на три уровня:

```text
src/app/globals.css              точка входа глобального CSS
src/styles/
  tokens.css                     custom properties дизайн-системы
  base.css                       reset, document defaults, focus, selection
  layout.css                     только общие container/section primitives
src/components/
  Header.module.css              структура, состояния и breakpoints Header
  FinePointerCursor.module.css   progressive enhancement курсора
  HeroField.module.css           canvas-слой
  sections/*.module.css          стили конкретной секции
  ui/*.module.css                стили переиспользуемого UI-примитива
```

`globals.css` импортирует три foundation-файла и не содержит компонентных селекторов. Альтернатива — оставить токены и reset непосредственно в `globals.css`; она проще по числу файлов, но сохраняет смешение точки входа и ответственности. Альтернатива CSS-in-JS отклонена из-за новой зависимости и ненужного клиентского runtime.

### 5. CSS Modules являются границей владения компонентом

Каждый компонент импортирует собственный `*.module.css` и получает локальные классы через объект `styles`. Состояния наподобие открытого меню выражаются комбинацией локальных классов, а не глобальным `.is-open`. Псевдоэлементы, дочерние селекторы и media queries остаются в модуле владельца.

Одинаково выглядящие, но семантически независимые элементы не объединяются только ради устранения нескольких строк CSS. Общий стиль выделяется лишь при наличии устойчивой общей роли. Это предотвращает появление нового глобального файла, связанного случайным визуальным сходством.

### 6. Глобальный слой имеет явный минимальный контракт

Глобальными остаются селекторы документа (`:root`, `*`, `html`, `body`, базовые `a`, `button`, `::selection`, `:focus-visible`) и два layout-примитива: `.container` и `.section`. Они используются многими серверными секциями и задают единый размер страницы и вертикальный ритм.

`skip-link` переносится к компоненту страницы либо в небольшой UI-компонент с собственным модулем; визуальный `status` оформляется как общий UI-примитив, если миграция подтверждает одинаковую структуру в Hero, Contact и Footer. Глобальные имена нельзя добавлять как обход CSS Modules без фиксации общей роли в `layout.css`.

Альтернатива — немедленно создать React-компоненты для каждого layout utility. Она отклонена: это расширяет рефакторинг CSS на структуру дерева и повышает риск изменения снимков без пользовательской ценности.

### 7. Токены описывают роли, а не каждое значение

В `tokens.css` сохраняются существующие цветовые переменные и добавляются только повторяющиеся значения с общей семантикой: ширина страницы, вертикальный ритм секций, высота header, z-index слоёв, типовые границы и длительности motion. Локальные геометрические значения остаются в модуле компонента.

Breakpoint-значения `900px` и `620px` документируются и одинаково применяются в модулях. Они не маскируются custom properties, поскольку CSS custom properties нельзя надёжно использовать в условиях `@media`. Container queries не вводятся: это изменило бы модель адаптивности и усложнило сравнение поведения.

### 8. Декоративные эффекты детерминированы и останавливаемы

`HeroField` получает воспроизводимую начальную геометрию из локального seeded generator либо детерминированной формулы, не зависящей от глобального состояния. При reduced motion отрисовывается один и тот же статичный кадр. При обычном motion цикл запускается только для видимого canvas и останавливается при unmount, скрытой вкладке или выходе слоя из области наблюдения, если это не меняет видимый результат.

`FinePointerCursor` сохраняет текущую инерцию, но не поддерживает бесконечный цикл до первого движения и после стабилизации координат. Новый frame запрашивается событием движения и продолжается лишь до достижения визуального покоя. Альтернатива — удалить оба эффекта — отклонена как визуальное изменение вне scope.

### 9. Порядок миграции минимизирует каскадные расхождения

Миграция выполняется снизу вверх: foundation, UI-примитивы, простые серверные секции, сложные секции, затем клиентские компоненты и page shell. Для каждого владельца правила сначала копируются в модуль без дизайнерского упрощения, импорт подключается в JSX, после чего исходные глобальные правила удаляются. Одновременное существование двух активных наборов правил не допускается дольше одного шага проверки.

Форматирование, переименование токенов и дедупликация выполняются отдельно от механического переноса, чтобы при визуальном расхождении было понятно, какой тип изменения его вызвал.

### 10. Существующие проверки являются acceptance gate

Тестовые файлы и снимки не меняются. После миграции должны проходить `typecheck`, `lint`, content tests, production build и существующий `test:visual`. Любой visual diff рассматривается как дефект рефакторинга; обновление snapshot не является допустимым способом завершить задачу.

Дополнительно реализация проверяется статически: в `globals.css` и `src/styles` не должно остаться селекторов конкретных компонентов, а JSX не должен ссылаться на мигрированные глобальные имена. Эти проверки выполняются ревью и поиском по коду, без добавления новых автотестов.

## Risks / Trade-offs

- [Разделение файла меняет порядок каскада и может повлиять на специфичность] → переносить стили по компонентам без параллельного редизайна, сохранять порядок правил внутри модуля и прогонять визуальные тесты после логических групп.
- [CSS Modules усложнят составные и условные className] → использовать простое объединение локальных классов без новой helper-зависимости.
- [Общие элементы будут преждевременно раздроблены или абстрагированы] → выделять только подтверждённые foundation/layout-роли; дублирование локального декларативного правила допустимо, если компоненты не разделяют ответственность.
- [Media queries повторятся в нескольких файлах] → принять контролируемое повторение двух документированных breakpoint-значений ради локальности компонента.
- [Глобальное состояние `has-fine-cursor` пересекает границу модуля] → оставить один явно обозначенный `:global(...)` bridge внутри модуля `FinePointerCursor`, не расширяя его на другие компоненты.
- [Существующие full-page snapshots чувствительны к среде] → использовать ту же зафиксированную версию Playwright/Chromium и не смешивать миграцию со сменой зависимостей или календарно-зависимого контента.
- [Перенос root layout может изменить стратегию рендеринга или обработку неизвестной локали] → использовать документированный Next.js 16 locale layout pattern, сохранить `notFound()` и проверить build output для `/ru` и `/en`.
- [Общий locale registry случайно попадёт в client bundle вместе со всем контентом] → отделить лёгкие locale-константы и типы от импортов RU/EN content objects.
- [Оптимизация animation loop изменит ощущение движения] → сохранить формулы интерполяции и визуальные параметры, меняя только условия запуска и остановки кадров.

## Migration Plan

1. Выделить locale registry, перенести locale-aware layout под динамический сегмент и удалить request-header bridge, сохранив `/`, `/ru`, `/en` и unknown-locale поведение.
2. Проверить и сузить server/client boundaries до минимальных интерактивных островов.
3. Создать foundation-файлы и превратить `globals.css` в стабильную точку импорта, не меняя вычисленные стили.
4. Перенести общие UI-примитивы и серверные секции в CSS Modules вместе с их responsive-правилами.
5. Перенести Header, Hero, HeroField и FinePointerCursor, одновременно сделав декоративные циклы детерминированными и останавливаемыми.
6. Удалить оставшиеся компонентные правила из глобального слоя и выполнить полный существующий набор проверок, включая visual regression.
7. При необходимости отката вернуть прежний root layout/proxy bridge, импорты глобального файла и строковые className; контент и snapshots миграции не требуют.

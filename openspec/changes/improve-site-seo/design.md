## Context

См. `proposal.md` — Why. Сейчас `/ru` и `/en` статически генерируются из типизированного контента; `generateMetadata` задаёт только title и description, `robots.ts` разрешает весь сайт, sitemap и JSON-LD отсутствуют, а `/` перенаправляется на `/ru`. Основной контент серверный и семантически организован (один H1, H2/H3, crawlable ссылки), но интерактивные Header, Timeline и canvas создают область для контроля производительности.

Проект работает на Next.js 16.3.5, поэтому реализация должна следовать установленной документации `node_modules/next/dist/docs`, а не предполагать API прежних версий. Публичный домен и доступ к Search Console/Bing из репозитория не следуют; план предусматривает явную production-конфигурацию и ручные операции владельца без секретов в git.

## Goals / Non-Goals

**Goals:**

- Сделать поисковые сигналы обеих локалей полными, непротиворечивыми и доступными в исходном HTML.
- Свести абсолютные URL к одному источнику истины и сделать ошибочную production-конфигурацию заметной до deploy.
- Описать одну и ту же сущность Person устойчивым JSON-LD графом, не дублируя факты вручную.
- Добавить автоматические проверки SEO-контракта и практический post-release цикл измерений.
- Сохранить статическую генерацию, небольшой browser bundle и текущую визуальную композицию.

**Non-Goals:**

- Гарантировать место, срок индексации, rich result или рост трафика.
- Создавать блог, программные landing pages, doorway pages, искусственные backlinks или массовый AI-контент.
- Добавлять неподтверждённые достижения, отзывы, рейтинги, работодателей или профили.
- Включать рекламную аналитику, cookies либо сторонний RUM без отдельного решения о приватности.
- Превращать якорные секции одностраничного CV в отдельные индексируемые URL без достаточного уникального контента.

## Decisions

### 1. Один валидируемый production origin

Ввести серверную SEO-конфигурацию с `siteUrl`, нормализованным до origin без завершающего `/`. В production принимается только абсолютный HTTPS URL; неверное или отсутствующее значение ломает сборку. Локальная разработка может использовать явно заданный development fallback, который не попадёт в production.

Этот origin используется `metadataBase`, canonical/alternates, sitemap, robots и JSON-LD. Альтернатива — собирать URL из request headers — отклонена: proxy и preview hosts способны породить разные canonical. Жёстко зашить домен тоже нельзя, пока фактический адрес не подтверждён.

### 2. Metadata API как источник head-сигналов

Расширить локализованные SEO-поля в типизированном контенте или отдельной типизированной SEO-карте и формировать через серверный `generateMetadata`: title, description, canonical, language alternates (`ru`, `en`, `x-default`), robots, Open Graph и Twitter. `x-default` ведёт на `/ru`, потому что туда ведёт корневой redirect; каждая локаль canonical сама на себя.

Head-теги вручную и клиентское изменение metadata отклонены: встроенный API согласует серверный вывод и специальные metadata routes. Keywords meta не добавляется — он не является полезным сигналом Google; релевантность усиливается видимым текстом.

### 3. Маленький локализованный sitemap и robots из общей конфигурации

Добавить `src/app/sitemap.ts` с двумя canonical URL и взаимными language alternates. `lastModified` включать только при наличии достоверной даты контентного релиза; нельзя подставлять текущее время каждой сборки как ложный freshness signal. `changeFrequency`/`priority` опциональны и не используются как обещание ранжирования.

`robots.ts` получает абсолютный sitemap URL и явный production host. `/` остаётся redirect и в sitemap не попадает. Для двух страниц отдельные sitemap-файлы и IndexNow усложнят систему без заметной пользы; Bing может обнаружить карту из robots и кабинета.

### 4. JSON-LD граф ProfilePage → Person

В server page отрисовать нативный `<script type="application/ld+json">` с графом `ProfilePage` и `Person`. `@id` строятся от canonical (`/ru#profile-page`, `/#person` или эквивалентная стабильная схема), а name, role/description, location, skills и `sameAs` берутся только из существующего типизированного контента. Межъязыковые страницы могут указывать на одну Person entity при локализованных ProfilePage URL.

Payload сериализуется с заменой `<` на `\\u003c`. `ProfilePage` выбран вместо `WebSite`-only разметки, потому что основной объект CV — один человек; `WebSite` можно включить в тот же граф только если он добавляет непротиворечивый site identity. `JobPosting`, `Review` и фиктивные InteractionCounter исключены как несоответствующие странице.

### 5. Social-preview asset как часть SEO-доставки

Добавить статическое или build-time изображение 1200×630 с безопасными полями, читаемыми именем и ролью; локализовать, если текст на картинке существенно различается. Metadata указывает абсолютный image URL, размеры и alt. Twitter использует large image card; OG locale отражает язык страницы и alternate locale.

Генерация на каждый запрос отклонена: контент меняется редко, а статический/build-time asset проще кэшировать и тестировать. Social metadata не является прямой гарантией ранжирования, но улучшает качество распространения и потенциальный CTR из внешних каналов.

### 6. Контентная оптимизация только через полезный видимый текст

Отредактировать hero summary, role, about, project contributions/results и при необходимости intro обеих локалей так, чтобы первая экранная область ясно связывала имя с backend/data/API специализацией, а кейсы содержали конкретные задачи и подтверждённые результаты. Сохранить структурное соответствие RU/EN и один H1; декоративный список технологий не должен быть единственным местом, где раскрываются компетенции.

Keyword stuffing, скрытый текст и одинаковые шаблонные повторы исключены. Исследование запросов после появления Search Console data используется для редакционных итераций, но не для изменения фактов.

### 7. Многоуровневая проверка и измерение

Unit/integration проверки анализируют результаты metadata helpers, sitemap/robots и JSON-LD. Production smoke test запрашивает `/`, `/ru`, `/en`, `/robots.txt`, `/sitemap.xml`, проверяет status/redirect, rendered HTML, один H1, canonical reciprocity, hreflang reciprocity, абсолютные URL, JSON parse и внутренние ссылки. Существующий Playwright production server переиспользуется, где это разумно.

Lighthouse или аналогичный лабораторный аудит фиксирует baseline, но не подменяет field data. После deploy владелец подтверждает ресурс в Google Search Console и Bing Webmaster Tools, отправляет sitemap, инспектирует обе страницы и сохраняет датированный baseline. Оценка проводится после периода переиндексации по локалям и query/page dimensions; изменения позиций не приписываются одной правке без достаточных данных.

## Risks / Trade-offs

- [Неизвестен финальный домен] → Сделать HTTPS origin обязательной deployment-конфигурацией и отдельным prerelease checklist item.
- [Ошибочные hreflang/canonical разделят сигналы] → Генерировать их одной pure-функцией и тестировать взаимность обеих локалей.
- [Structured data расходится с UI] → Строить его из той же content model и валидировать JSON плюс соответствие ключевых полей видимому тексту.
- [Непроверенный JSON-LD текст создаёт XSS] → Серверная сериализация с экранированием `<`, без user-generated HTML.
- [Фальшивый `lastModified` снижает доверие к sitemap] → Использовать дату контентного релиза либо не включать поле.
- [SEO-копирайтинг ухудшит живой голос CV] → Редакторская проверка обеих локалей и запрет на частотные повторы/скрытый текст.
- [Canvas/клиентская интерактивность ухудшат INP/LCP] → Измерить baseline, профилировать только подтверждённые узкие места и сохранить основной контент server-rendered.
- [Инструменты поисковиков требуют внешнего доступа и времени] → Разделить автоматизируемый release gate и ручной post-release checklist; не считать индексацию мгновенной.

## Migration Plan

1. Подтвердить production origin и способ передачи публичной конфигурации в build/deploy.
2. Добавить общую SEO-конфигурацию и локализованную content model; покрыть их unit-тестами.
3. Выпустить metadata, JSON-LD, social image, sitemap и robots одной согласованной партией.
4. Выполнить production build и smoke/visual/SEO regression checks; проверить structured data валидаторами.
5. Развернуть без изменения существующих `/ru`, `/en` и root redirect; проверить реальные response headers и HTML.
6. Подтвердить ресурсы, отправить sitemap и зафиксировать baseline в Google Search Console/Bing Webmaster Tools.
7. При регрессии откатить SEO-партию целиком; текущие страницы сохранят базовые title/description и доступность, а кабинеты переобойдут предыдущую версию.

## Open Questions

- Какой HTTPS origin будет production-каноническим? Ответ нужен перед реализацией конфигурации/deploy, но не меняет контракт или разбивку задач.
- Какие подтверждённые публичные профили, кроме GitHub, разрешено включить в `sameAs`? При отсутствии подтверждения остаётся только GitHub.
- Доступны ли владельцу Google Search Console и Bing Webmaster Tools? Если нет, кодовая часть остаётся полной, а эксплуатационные пункты будут ожидающими внешней настройки.

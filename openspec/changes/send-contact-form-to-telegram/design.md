# Design

## Context

`Contact` в `src/components/sections/Contact.tsx` пока не содержит формы. Change `add-contact-form` определяет локализованную форму, ее клиентскую проверку, визуальный контракт и вызов `POST /api/contact`. Этот change реализует только серверный endpoint и пересылку сообщения в Telegram. См. `proposal.md` и `specs/interactive-contact-and-footer/spec.md`.

Приложение использует Next.js 16 App Router, React 19 и Node.js. Текущий код не содержит `src/app/api`, новой runtime-зависимости или базы данных. Документация production в репозитории указывает Docker/VPS, хотя целевым окружением этой интеграции является Vercel. Route Handler и отправка через HTTPS остаются переносимыми; Vercel-specific rate limiting и переменные окружения требуют сверки с фактическим deployment-проектом.

## Goals / Non-Goals

**Goals:**

- Добавить один небольшой публичный endpoint для уже существующей формы и сохранить локальную валидацию формы как удобство, а не как границу безопасности.
- Доставлять сообщение синхронным запросом к Telegram Bot API, используя серверный Node.js runtime и один настроенный `chat_id`.
- Возвращать понятный стабильный контракт ответа, чтобы форма сообщала успех только при подтверждённой доставке и сохраняла значения при ошибке.
- Ограничить входные данные и частоту обращений, не добавляя постоянное хранилище или отдельный сервис.
- Не передавать секреты и содержимое формы в браузер, клиентские ошибки или логи приложения.

**Non-Goals:**

- Создание Telegram-бота, обработка команд, webhook, ответ пользователю из Telegram или управление несколькими целевыми чатами.
- Переработка дизайна, структуры полей и локализованных текстов формы.
- Сохранение заявок, очередь повторной доставки, вложения, CAPTCHA или аналитика.
- Поддержка темы форума Telegram или доставки в несколько чатов.

## Decisions

### 1. Использовать Next.js Route Handler `POST /api/contact`

Создать `src/app/api/contact/route.ts` с экспортом `POST`. Handler работает в Node.js runtime по умолчанию и принимает только JSON. Это соответствует App Router, не требует отдельного API-сервиса и позволяет сохранить токен на сервере.

Альтернативы: Server Action связывает отправку с React-переходом формы, но хуже подходит для явно заданного HTTP-контракта и самостоятельной проверки endpoint; внешний form-service добавляет ещё один получатель персональных данных и зависимость. Оба варианта не нужны для одного уведомления.

### 2. Зафиксировать небольшой JSON-контракт и повторно валидировать все поля на сервере

Запрос содержит `name`, `email`, `message`; локализованные строки и состояние UI не входят в контракт. Проверка на сервере выполняется до внешнего вызова: требовать JSON, ограничить всё тело 16 KiB, после trim проверять непустое имя/email/сообщение, длины 120/254/1500 Unicode-символов и базовый синтаксис email. Переносы строк сообщения сохраняются; управляющие символы, кроме переводов строк и табуляции, удаляются или нормализуются.

Не добавлять схему-валидатор для трёх строк: текущий проект не имеет runtime-зависимостей для форм, а контракт достаточно мал для отдельной чистой функции с тестами. Клиентская проверка остаётся для UX и не считается доверенной.

Ответы endpoint: `200 { ok: true }` при доставке; `400` при некорректных данных; `413` при превышении лимита тела; `415` при неподдерживаемом Content-Type; `429` при блокировке rate limit; `502` при ошибке/тайм-ауте Telegram; `503` при отсутствующей серверной конфигурации. Ошибки используют стабильный безопасный `code`, не включающий тексты полей или ответ Telegram.

### 3. Отправлять напрямую через Telegram Bot API без SDK

Сформировать plain-text сообщение из имени, обратного email и сообщения, затем вызвать `https://api.telegram.org/bot<TOKEN>/sendMessage` через серверный `fetch` с `chat_id` из окружения. Не задавать `parse_mode`: пользовательский текст не должен интерпретироваться как HTML/Markdown. Проверять и HTTP-статус, и поле `ok` JSON-ответа Telegram. Использовать ограниченный тайм-аут, например 8 секунд.

Не использовать webhook: сайт только отправляет исходящие уведомления, он не принимает обновления Telegram. Не добавлять Telegram SDK, потому что необходим один прямой HTTP-вызов.

Автоматически не повторять запрос после тайм-аута: Telegram мог принять сообщение, а ответ потеряться; автоматический повтор способен создать дубликат. В таком неопределённом случае вернуть общую ошибку доставки и оставить ручное повторное действие форме.

### 4. Хранить токен и адресата только в серверных переменных окружения

Использовать `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Не добавлять `NEXT_PUBLIC_`, не включать секреты в source code, `next.config`, клиентские props или `.env.example`. Создать переменные отдельно для Vercel Preview и Production; Preview должен использовать тестовый бот/чат или оставаться без production-токена.

Перед production-развёртыванием владелец должен начать личный диалог с ботом через `/start` либо добавить бота в целевую закрытую группу, а затем установить соответствующий `chat_id`. Telegram не позволяет боту первым начать личный диалог.

### 5. Ограничивать поток на Vercel Firewall, а не в памяти функции

Настроить правило rate limit для `POST /api/contact` с ключом IP и умеренным фиксированным окном. Endpoint должен корректно преобразовать блокировку в `429`, если она выполняется приложенческим middleware; если запрос отсекает Firewall до вызова функции, пользовательский ответ и статус определяются конфигурацией Firewall. Не полагаться на `Map`/память Node.js как на общий лимитер: экземпляры serverless-функции не разделяют состояние. Для локального запуска отсутствие внешнего лимитера не должно влиять на функциональные тесты handler.

Если фактический production остаётся на Docker/VPS вместо Vercel, потребуется эквивалентное ограничение в reverse proxy или общее хранилище лимитера; добавление такого сервиса не входит в текущий scope. Текущие deployment docs противоречат заявленному Vercel deployment, поэтому это нужно сверить до production настройки.

### 6. Сохранять минимальный след персональных данных

Не хранить заявки в базе, файлах, cookies, analytics или application logs. В лог писать только request correlation ID, исход/код результата и технический статус внешнего вызова; не писать имя, email, текст, токен и URL Telegram с токеном. В клиентском ответе не раскрывать детали Bot API.

## Risks / Trade-offs

- **[Risk]** Публичный endpoint могут использовать для спама или исчерпания лимитов Telegram. → **Mitigation:** ограничить размер/поля, включить honeypot на форме при её интеграции и задать path-specific rate limit в Vercel Firewall; CAPTCHA оставить для случая реального спама.
- **[Risk]** Плохая конфигурация `chat_id` или отсутствие `/start` приведёт к отказам доставки. → **Mitigation:** вручную проверить токен и целевой чат в тестовом deployment перед включением формы в Production; в логах оставить только безопасный тип/код ошибки.
- **[Risk]** Тайм-аут может произойти после фактической отправки Telegram, и пользователь может повторить заявку. → **Mitigation:** не делать автоматические повторы и честно сообщать о неопределённом результате; возможный единичный дубль допустим без постоянного хранилища и idempotency-store.
- **[Risk]** Персональное сообщение передаётся в Telegram и становится видимым адресатам настроенного чата. → **Mitigation:** использовать приватный личный чат или закрытую группу с ограниченным составом и ясно сообщить посетителю, куда отправляются данные.
- **[Risk]** В репозитории production описан как Docker/VPS, а интеграция настраивается под Vercel. → **Mitigation:** до deployment проверить фактическое окружение; сохранить endpoint host-agnostic, а rate limit и секреты настроить для реального хоста.

## Migration Plan

1. Согласовать контракт ответа endpoint с `openspec/changes/add-contact-form`: форма показывает успех только после подтверждённой доставки, а значения остаются в полях при ошибках.
2. Реализовать и локально проверить POST endpoint с замоканным Telegram API; реальные токен и чат не требуются для unit/component тестов.
3. Создать тестовый Telegram-бот/чат и проверить отправку в Vercel Preview с отдельными секретами.
4. Настроить ограничение частоты для endpoint, добавить production-переменные в Vercel и выполнить проверочную отправку после deployment.

Откат: скрыть/отключить отправку в форме и вернуть локализованное уведомление о временной недоступности, затем удалить endpoint либо оставить его выключенным без серверных секретов. Прямую email-ссылку сохранить. Ранее доставленные сообщения отозвать невозможно.

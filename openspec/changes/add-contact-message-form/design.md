# Design

## Context

`Contact` сейчас является серверно-рендеримым компонентом с двумя колонками прямых ссылок и без формы. Общие `.section`/`.container` используют крупные вертикальные отступы и ограниченную ширину страницы, поэтому контактный блок потребует локального layout-override. Контент проекта локализован в `src/content/ru` и `src/content/en`, а интерактивные сценарии проверяются Vitest и Playwright.

См. `proposal.md` для мотивации и `specs/interactive-contact-and-footer/spec.md` для изменённого поведенческого контракта.

## Goals / Non-Goals

**Goals:**

- Сохранить server-rendered текст, SEO и прямые контакты, вынеся только интерактивную часть формы в клиентский слой.
- Сделать контактную композицию полноширинной в пределах viewport с небольшими page-edge gutters и без общего большого `--section-space`.
- Дать форме предсказуемые локальные состояния: pristine, validation error и validated-but-not-delivered.
- Переиспользовать текущие токены `--carbon`, `--graphite`, `--paper`, `--steel`, `--signal`, `--rule`, чтобы визуально отличаться от оранжево-красного референса и оставаться частью сайта.
- Сохранить доступность: видимые подписи, `aria-describedby`/`aria-invalid`, live-region для результата и управляемый фокус.

**Non-Goals:**

- Серверный endpoint, отправка email, интеграция с Formspree/CRM, аналитика и хранение пользовательских данных.
- Новый state-management или библиотека валидации.
- Ручная resize-ручка у `textarea`, drag-and-drop файлов и вложения.
- Изменение footer, hero, навигации или общей палитры сайта вне локального контактного блока.

## Decisions

### 1. Отдельный клиентский `ContactForm` внутри серверного `Contact`

`Contact` продолжает принимать локализованный `ContactContent` и рендерить заголовок/контакты. Форма выделяется в небольшой компонент с `"use client"`, который получает только локализованные строки и значения лимитов. Это сохраняет серверный HTML для основного контента и ограничивает клиентский JavaScript интерактивной формой.

Рассматривалась конвертация всего `Contact` в client component, но она увеличила бы клиентскую границу без необходимости и смешала бы статичный контент с локальным состоянием формы.

### 2. Нативная форма плюс точечная клиентская проверка

Использовать стандартные `form`, `input`, `textarea`, `button`, `required`, `type="email"`, `minLength`/`maxLength` и `noValidate` только если потребуется единый локализованный вывод ошибок. Собственная проверка выполняется на submit и blur/change после первой ошибки; результат хранится в локальном React state. Поля получают `autocomplete="name"` и `autocomplete="email"`, а paste/autofill не перехватываются.

Рассматривалась библиотека схем валидации, но для трёх полей она создаёт лишнюю зависимость и не даёт преимуществ при отсутствии серверного контракта.

### 3. Отправка остаётся полностью локальной

`onSubmit` вызывает `preventDefault()`, проверяет значения и при успехе устанавливает `status="not-delivered"`. Сетевые API (`fetch`, form action, внешние POST) не используются. Значения остаются в полях, а сообщение результата выводится через `role="status"` и `aria-live="polite"`. Прямая `mailto:`-ссылка остаётся рядом с формой.

Это явно отличается от референсной иллюзии отправленного сообщения: интерфейс может сообщить состояние формы, но не должен утверждать, что письмо реально доставлено.

### 4. Полноширинная композиция без пустого ведущего столбца

Для секции использовать собственный shell с `width: 100%`, небольшим горизонтальным padding и уменьшенным локальным `padding-block`. Внутри — CSS Grid без искусственного пропуска колонок: на desktop форма занимает основной столбец, а прямые контакты — соседний столбец, начинающийся сразу от своей границы. Заголовок и поле сообщения получают достаточно ширины, а контактные строки не начинаются после пустого `grid-column`.

На tablet/mobile grid переходит в одну колонку. Контакты располагаются после формы, сохраняют верхние/нижние разделители и не требуют горизонтальной прокрутки. Для `textarea` задаётся контролируемая минимальная высота и `resize: none`; длинный ввод прокручивается внутри поля или раскрывается только через предусмотренное стилями поведение, без ручной drag-ручки.

Рассматривалось сохранение общего `.container` и прежней сетки `1 / span 6` + `8 / -1`, но это оставляет визуальный воздух и противоречит требованию полноширинной формы.

### 5. Контентная модель остаётся двуязычной

Расширить `ContactContent` структурой строк формы: labels, placeholders, submit label, validation messages и local-only result message. Удалить зависимость новой композиции от `contact.status`, чтобы в форме не появлялся текст про открытость к предложениям; прямые контактные поля (`email`, `phone`, `github`, `location`) сохранить.

Это позволяет проверять равенство структуры RU/EN существующими content-тестами и не зашивать русский/английский текст в JSX.

### 6. Проверка поведения и визуального контракта

- В Vitest проверять наличие формы, связанных labels, типов полей, `autocomplete`, прямой email-ссылки и отсутствие текста статуса/сетевого action.
- В Playwright добавить сценарии для валидной локальной отправки, invalid submit с фокусом на первом ошибочном поле, очистки/сохранения значений, отсутствия запросов и responsive layout на desktop/tablet/mobile.
- Дополнить визуальные snapshots только после ручной проверки обеих локалей; текущие reference snapshots считать намеренно изменяемыми для этой дизайн-фичи.

## Risks / Trade-offs

- **[Risk]** Нативный autofill браузера может визуально переопределять фон и цвет текста. → **Mitigation:** стилизовать `:-webkit-autofill`/`autofill` в рамках текущих токенов и не полагаться только на placeholder.
- **[Risk]** Локальная форма может быть ошибочно воспринята как реально отправляющая сообщения. → **Mitigation:** использовать явный локализованный текст о неподключённой доставке и сохранять `mailto:`-альтернативу.
- **[Risk]** Уменьшенные отступы и полноширинный layout могут ухудшить читаемость на узком экране. → **Mitigation:** задать breakpoint-правила, ограничить длину текстовых строк и прогнать существующие viewport-проверки.
- **[Risk]** Изменение высоты контактной секции сломает page-level snapshots. → **Mitigation:** обновлять snapshots только после проверки переносов, фокуса, ошибок и обеих локалей.

## Migration Plan

Миграция данных не требуется: форма не хранит значения после ухода со страницы и не меняет API. Реализация выкатывается как обычное frontend-изменение вместе с локализованным контентом и тестами. Откат — удалить новый `ContactForm`, вернуть прежнюю разметку/стили и восстановить предыдущие snapshots; серверные сервисы при этом не затрагиваются.

## Purpose

Определяет надёжную и проверяемую автоматическую доставку версии сайта из ветки `main` GitHub-репозитория в production за существующим Nginx.

## ADDED Requirements

### Requirement: Deployment запускается изменением main
Система SHALL запускать production pipeline для каждого нового commit в ветке `main`, включая прямой push и merge pull request, и SHALL позволять повторный ручной запуск для того же commit.

#### Scenario: Прямой push в main
- **WHEN** новый commit отправлен непосредственно в `main`
- **THEN** запускается production pipeline для SHA этого commit

#### Scenario: Слияние pull request
- **WHEN** pull request из другой ветки слит в `main`
- **THEN** запускается production pipeline для итогового merge commit в `main`

#### Scenario: Ручной повтор
- **WHEN** уполномоченный пользователь вручную запускает workflow для выбранного commit из `main`
- **THEN** система повторяет production pipeline для выбранного SHA без необходимости создавать новый commit

### Requirement: Проверки блокируют публикацию
Система MUST выполнять установку зависимостей из lock-файла, lint, проверку типов, автоматические тесты и production-сборку до начала deployment. При неуспехе любой обязательной проверки production SHALL оставаться на предыдущей версии.

#### Scenario: Все проверки успешны
- **WHEN** все обязательные проверки commit завершились успешно
- **THEN** pipeline разрешает сборку и доставку production-образа

#### Scenario: Проверка завершилась ошибкой
- **WHEN** хотя бы одна обязательная проверка commit завершилась ошибкой
- **THEN** pipeline останавливается до изменения production-сервиса

### Requirement: Неизменяемый и идентифицируемый образ
Система SHALL публиковать production-образ с неизменяемым тегом, связанным с полным Git commit SHA, и SHALL разворачивать именно этот тег, а не плавающий тег вроде `latest`.

#### Scenario: Публикация образа
- **WHEN** проверки commit успешны и Docker-образ собран
- **THEN** registry содержит образ, однозначно связанный с SHA этого commit

#### Scenario: Deployment выбранной версии
- **WHEN** сервер получает команду deployment
- **THEN** он загружает и запускает образ с ожидаемым commit SHA

### Requirement: Секреты и доступы защищены
Система MUST хранить SSH-ключи, registry credentials и параметры production вне репозитория, ограничивать GitHub workflow минимально необходимыми permissions и выполнять серверные операции от отдельного непривилегированного deploy-пользователя.

#### Scenario: Чтение конфигурации pipeline
- **WHEN** пользователь просматривает содержимое репозитория и логи обычного успешного workflow
- **THEN** приватный SSH-ключ и registry token не раскрываются

#### Scenario: Подключение к неизвестному серверу
- **WHEN** SSH host key сервера не совпадает с доверенным значением
- **THEN** deployment прекращается до выполнения удалённых команд

### Requirement: Совместимость с существующим Nginx
Production-контейнер SHALL обслуживать приложение на порту `3000`, опубликованном только на `127.0.0.1`, чтобы публичный HTTP/HTTPS-трафик продолжал проходить через существующий Nginx и его Certbot-сертификаты.

#### Scenario: Контейнер запущен
- **WHEN** production-сервис находится в рабочем состоянии
- **THEN** приложение доступно Nginx по `http://127.0.0.1:3000` и порт `3000` не опубликован на внешних интерфейсах сервера

#### Scenario: Запрос к домену по HTTPS
- **WHEN** клиент открывает `https://artem-trikula.ru`
- **THEN** Nginx терминирует TLS и проксирует запрос в production-контейнер

### Requirement: Deployment подтверждается проверкой доступности
Pipeline SHALL считать deployment успешным только после успешного health check контейнера и проверки публичного HTTPS endpoint. Одновременно SHALL выполняться не более одного production deployment.

#### Scenario: Новая версия доступна
- **WHEN** новый контейнер здоров и публичный endpoint отвечает ожидаемым успешным HTTP-статусом
- **THEN** pipeline помечает deployment успешным и сохраняет идентификатор развернутого образа

#### Scenario: Проверка новой версии не прошла
- **WHEN** контейнер не становится здоровым или публичный endpoint не проходит проверку за заданное время
- **THEN** pipeline завершается ошибкой и предоставляет достаточно данных для диагностики и отката

#### Scenario: Новый commit приходит во время deployment
- **WHEN** production deployment уже выполняется и для `main` запускается следующий
- **THEN** система сериализует или отменяет устаревший запуск так, чтобы удалённые операции не выполнялись конкурентно

### Requirement: Production можно откатить
Оператор MUST иметь документированную процедуру возврата к последнему известному рабочему SHA без пересборки образа, если соответствующий образ ещё хранится в registry.

#### Scenario: Откат на предыдущую версию
- **WHEN** оператор выбирает SHA последнего известного рабочего образа и запускает процедуру отката
- **THEN** сервер запускает выбранный образ и повторяет те же проверки готовности, что и обычный deployment
